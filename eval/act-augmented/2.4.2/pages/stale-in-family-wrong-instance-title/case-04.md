# case-04 — Release notes: title pinned to v4.1.0 on the v4.2.0 release-notes page

## Scenario
A developer-documentation release-notes page generated by a static-site generator from
markdown + front matter. The body is unambiguously the **v4.2.0** release notes: the
version `<select>` shows "v4.2.0 (current)" selected, the `<h1>` reads "Release notes —
Quartzdb v4.2.0", the release date and package line read `quartzdb@4.2.0`, the Upgrade
section is "Upgrading from 4.1.0 to 4.2.0", the install snippet pins `quartzdb@4.2.0`,
and every changelog item is scoped to 4.2.0. The `<title>`, however, reads **"Release
notes — v4.1.0 · Quartzdb Documentation"** — the version was bumped everywhere except
the page's front-matter `title:` field, from which the generator builds `<title>`. v4.1.0
is a *real prior release* with its own page in the docs set, so the title is plausible.

## Attribute tuple + developer persona
- **content-domain:** developer docs / API reference
- **UI component / pattern:** docs sidebar + version `<select>` switcher + changelog lists + code blocks
- **host-language construct:** `<title>` rendered from a markdown front-matter `title:` field (SSG-built head)
- **locale / i18n:** en, semantic versioning (`4.x.y`)
- **failure-mechanism:** version bumped in body + heading, stale in the page-meta `title:` front matter
- **developer persona:** A maintainer cut the 4.2.0 release, copied the 4.1.0 release-notes
  markdown file to start the new one, rewrote the H1 and all changelog bullets, but left
  the YAML front matter `title: "Release notes — v4.1.0"` at the top of the file. The
  generator's `<head><title>` comes from that field, not the H1, so the build produced a
  4.1.0 title over 4.2.0 content. The old 4.1.0 page still exists at its own URL.

## Element / selector carrying the issue
- `head > title` — `Release notes — v4.1.0 · Quartzdb Documentation`
- Contradicted by `select#ver` (selected `v4.2.0 (current)`), `main h1#rn-h1`
  (`Release notes — Quartzdb v4.2.0`), `.reldate` (`quartzdb@4.2.0`), the Upgrade prose
  (`Upgrading from 4.1.0 to 4.2.0`), the install `pre>code` (`npm install quartzdb@4.2.0`),
  the "What's new in 4.2.0" / "Bug fixes in 4.2.0" headings, and the footer
  (`Quartzdb v4.2.0 release notes`).

## Exact accessibility mechanism (what AT experiences and why it fails)
A screen-reader user hears "Release notes — v4.1.0" on tab announcement, page load, in a
tab/window list, in history, and in bookmarks. The page is the **4.2.0** notes
throughout. Note the body deliberately *mentions* 4.1.0 in context ("Upgrading from 4.1.0
to 4.2.0", "regression present since 4.1.0") — so a naive reader (or matcher) finds
"4.1.0" present in the body and might wrongly conclude the title agrees. The decisive
identifier — the version this page *is about* — is 4.2.0, set by the H1, the selected
version control, the release date, and the install pin. A blind developer comparing
release-notes tabs across versions, or trusting the title to confirm which version's
notes they are reading before pinning a dependency, is misdirected to the prior release.
This is the descriptiveness limb of F25, sharpened: the title's version is not absent
from the body, it is present but as a *referenced* version, not the page's *subject*.

## Why automated tools cannot detect it
axe-core, WAVE and Lighthouse confirm a present, non-empty `<title>` (ACT 2779a5) and
stop. "Release notes — v4.1.0 · Quartzdb Documentation" is valid, non-empty, unique,
product-qualified and on-topic. A keyword-overlap heuristic is actively *fooled* here:
"4.1.0" appears in both the title and the body (in the upgrade and regression sentences),
so naive title-vs-content overlap scores the title as consistent. Determining the page's
true subject version (4.2.0) requires understanding that the H1 + selected version
control + install pin name the *subject*, while the body's "4.1.0" mentions are the
*previous* version referenced for context — a semantic distinction no linter or overlap
metric makes. Only a human (or model) reasoning about which version the page documents
catches that the title names the wrong release.

## Expected ACT-style outcome
**failed** (SC 2.4.2, technique F25 — title does not identify this page's subject version;
among versioned release-notes pages it names a different release).
