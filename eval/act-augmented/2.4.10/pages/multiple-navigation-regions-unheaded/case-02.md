# case-02 — API docs: site-section nav + in-page "On this page" nav, neither headed

## Scenario
A developer-docs page in the "Orbit Payments API reference" (the *Pagination* article) has
two navigation regions that serve **different navigational purposes**:
1. a **left site-section nav** — the docs tree (Authentication, Idempotent requests, Charges,
   Customers, Payouts, **Pagination** (current), Webhooks) that moves the reader *between*
   documents, and
2. a **right in-page "On this page" nav** (Overview / Cursor parameters / Response shape /
   Code examples) that jumps to anchors *within the current article*.

Both are real `<nav>` landmarks; the article itself has a clean `h1 → h2` outline. But
**neither navigation region carries a heading**. The only headings on the page are the
article's *content* headings. A screen-reader user jumping by heading lands on "Pagination",
"Overview", "Cursor parameters", etc. — the content — and never meets a heading that tells
them "this is the site navigation" versus "this is the on-this-page navigation."

## Attribute tuple
- **content-domain:** developer documentation / API reference
- **UI-component / pattern:** static-site-generator three-column docs layout (left docs tree + center article + right TOC)
- **host-language construct:** two `<nav>` elements (`nav.docnav`, `nav.toc`) wrapping `<ul>`s; content `<h1>`/`<h2>` inside `<article>`; the left nav uses non-heading `div.group-label` "Getting started"/"Core resources" sub-labels (styled text, NOT headings)
- **locale / i18n:** en-US
- **failure-mechanism:** H69 nav-demarcation — two distinct navigation sections (between-docs vs within-doc) each lack a demarcating heading; the visually-styled `group-label` divs masquerade as structure but carry no heading role

## Developer persona
The docs are generated by a static-site generator (Docusaurus-style theme) where the
right-hand "On this page" widget and the left sidebar are theme-provided components. The
theme emits `<nav>` wrappers (good landmarks) but renders the sidebar category labels
("Getting started", "Core resources") as styled `<div>`s, and renders the TOC with no label
at all. The team writes Markdown for the article body — which becomes the `h1`/`h2`s — and
never touches the theme chrome, so the navigation regions inherit the theme's heading-less
markup. It passes the team's axe CI check, so it ships.

## Element / selector carrying the issue
- `nav.docnav` (region 1, left site-section navigation) — no heading; its `.group-label`
  divs are styled text, not heading elements.
- `nav.toc` (region 2, right in-page navigation) — no heading at all.

The document's only headings (`main article h1`, `main article h2`) label article *content*,
not either navigation region.

## Exact accessibility mechanism (what AT experiences, why it fails)
- A sighted user sees a left rail (with "Getting started" / "Core resources" sub-labels), a
  center article, and a right rail visually titled by its position; they know which is which.
- A screen-reader user navigating by heading gets: "Pagination" (h1) → "Overview" (h2) →
  "Cursor parameters" (h2) → "Response shape" (h2) → "Code examples" (h2). None of these is
  a navigation-region heading. The two `<nav>` landmarks are reachable by landmark navigation,
  but H69's requirement is *heading* demarcation, and by heading there is no way to find,
  enter, or distinguish the site-section nav from the in-page nav.
- The `group-label` divs ("Getting started", "Core resources") visually imply structure but
  carry no heading role, so they do not appear in the headings list — the classic F2-style
  trap of conveying structure with presentation instead of semantic markup.
- Per H69 the page should "demarcate different navigational sections" with headings; here two
  genuinely different navigation sections are demarcated by none.

The defect is genuinely in the DOM: two heading-less `<nav>`s plus styled-`div` pseudo-labels.

## Expected ACT-style outcome
**failed** (SC 2.4.10 — H69 nav-demarcation sub-limb: two functionally distinct navigation
sections, neither introduced by a section heading; the visual sub-labels are not headings).

## Why automated tools miss it
The page has one `<h1>`, a sequential `h1 → h2` outline, two valid `<nav>` landmarks, no
empty headings, and no missing attributes, so axe-core, WAVE, and Lighthouse pass it (and ACT
047fe0 passes on the `<h1>`). An automated tool cannot tell that "Authentication / Charges /
Pagination" (a between-documents nav) and "Overview / Cursor parameters / Response shape" (a
within-document nav) are two distinct navigation purposes that each deserve a demarcating
heading — nor that the styled `group-label` divs *look like* section headings but aren't.
Recognizing that the links in each region do different jobs, and that a heading is needed to
orient a heading-navigating user, is exactly the human reading/visual judgment static rules
cannot perform.
