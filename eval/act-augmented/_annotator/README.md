# ACT-Augmented Annotator

A browser tool for human-judgment annotation of the `eval/act-augmented/` corpus
(923 hand-built pages across 22 WCAG SCs / 150 failure "aspects"). Separate from the
main `index.html` annotation tool — this one is purpose-built for the augmented dataset.

## Run it

The pages must be served **same-origin** so the highlight overlay can read each test
page's DOM. Start the repo's static server and open the tool through it:

```bash
npm start                     # serves the repo root on http://localhost:3001
```

Then open: **http://localhost:3001/eval/act-augmented/_annotator/index.html**

(Opening the file directly with `file://` is blocked — a banner explains why.)

## Practice first (calibration gate)

On first use the tool opens in **Practice mode**: a small set of **W3C ACT test cases**
(from `eval/checker-comparison/act-subset/`) with *authoritative* pass/fail outcomes, used to
calibrate your judgment before the real corpus. You get **2 cases per SC** — one that should
**fail** (an issue exists) and one that should **pass** (no issue), where the ACT set provides
them — scoped to **the SCs in your loaded filter** (so a work-split annotator practices only
their SCs). Each practice page shows the rule, the relevant **Trusted Tester** test (or the
WCAG **Understanding** doc when no single TT test fits), and one question — *does an issue
exist?* After you answer, it **reveals the ground truth** (correct / not quite + the ACT rule).
The **annotation queue stays hidden until every practice case is answered**; then it unlocks
automatically. Practice answers persist, so reloading keeps you unlocked. (Practice cases are
generated by `build-practice.js` → `practice/practice-cases.json`; the per-rule Trusted Tester
choice lives in `practice-tt-map.json`.)

## What you do per page — two pages

The right panel is a **two-page wizard**. The page's target element is **highlighted by
default** with a dimmed backdrop (a non-destructive overlay from the case's `primarySelector` —
it never injects into the page HTML). While the highlight is on, the **backdrop blocks clicks**
to the page (you can still scroll); **toggle ◎ Highlight off to interact** — which also starts
the screen reader (see below). **⟐ ANDI** manually launches SSA's
[ANDI](https://www.ssa.gov/accessibility/andi/help/install.html) inspector inside the page view
— it's **vendored locally** under `vendor/andi/`, so it loads offline with no ssa.gov download.
**◑ Contrast** opens the [WebAIM contrast checker](https://webaim.org/resources/contrastchecker/)
in a new tab, and **↗ Open in tab** opens the page in a new tab with ANDI launched there too.

**Page 1 — Apply the test.** The top segment is headed by the **aspect title** (e.g.
*"Partial update without aria-atomic announces only the changed fragment, losing meaning"*)
with the per-page **claimed mechanism** beneath it, then **How to test it** — scoped to the
**specific Trusted Tester test** that targets this aspect (e.g. SC 1.1.1's CSS-background-image
aspect shows only *Test 7.C*), with a *Show full SC test process* toggle. (For the 5 SCs TT
doesn't cover, the W3C **Understanding** doc is shown; for aspects no single TT test isolates,
the full SC process is shown.) A **screen-reader transcript + element inspector** dock sits under the page (shown once the
highlight is dismissed). It is split: the **left** half is the SR **transcript**; the **right**
half is the **element inspector** (ported from the original annotator). **Click any element in
the page** to inspect it — the inspector shows its **ROLE**, **KEYBOARD** (focusable?), **A11Y
TREE** status, and **NAME**, where the name is **Chrome's authoritative accessible name** fetched
live from the server's CDP `/ax-node` endpoint (so it matches DevTools' accessibility node — not
a heuristic). The inspector's **◀ Prev / Next ▶** drive the SR cursor through reading order and
**● Click** activates the current element; each step is logged to the transcript using the same
Chrome ax-node name. **✕** in the transcript corner clears it. The SR also **follows focus** — as
ANDI's prev/next move focus through the page, each focused element is announced (tagged `focus`) —
and **live-region announcements** are logged too (tagged `live` / `⚠ alert`). The transcript records your SR actions (initial `target` read,
`focus` moves) **and live-region announcements that should be made** — when an `aria-live` /
`role=status` / `role=alert` region updates it's logged tagged `live` (polite) or `⚠ alert`
(assertive), honouring `aria-atomic` / `aria-busy` / `aria-hidden` / `aria-live="off"` (this is
what makes the SC 4.1.3 Status-Messages cases testable). You answer **Q1 — *Does an accessibility
issue exist on this page?*** (Yes / No); *Decide* unlocks once Q1 is answered.

**Page 2 — Decide.** Shows **What this checks**, the **claimed mechanism**, **Why automated
tools miss it** (expanded), and **How to test it** (folded). You answer **Q2 — *Approve* the
case as described, or *Comment*** — a comment asks **why**: no error here / a different type of
error / problem with the page itself / other, plus a free-text note. **← Back** returns to the
test page; **Save & next** advances.

Keyboard: `←/→` or `p/n` navigate cases · `h` highlight · Page 1: `1/2` Q1, `Enter` decide ·
Page 2: `a/c` Q2, `b` back, `Enter` save. In **Practice mode**: `1/2` answer, `Enter` next.

## Data & logging

- Everything autosaves to `localStorage` (`act-aug-annotations/v1`).
- **⬇ Export** downloads a JSON with all annotations **and** an inspection **log**
  (case opens, highlight toggles, open-in-tab, answers, dwell time, navigation, etc.).
- **⚙** sets your annotator name (recorded in the log/export).

## Optional page filter

**⛶ Filter** loads a JSON limiting which pages appear (default = all 923). Accepted shapes:

```json
["1.1.1", "1.4.3/contrast-from-gradient", "2.4.4/link-purpose/case-02"]
```
```json
{"include": [{"sc":"1.1.1"}, {"sc":"2.4.4","aspect":"link-purpose"}]}
```

An SC-only selector includes the whole SC; SC+aspect the whole aspect; SC+aspect+caseId
one page. A loaded filter **persists in browser storage** and is reapplied on reload until you
**✕ Clear filter**.

### Seeded order + work splits

A filter object may also carry a **`seed`** and a **`slice`**, used to divide the dataset among
annotators deterministically:

```json
{ "include": ["1.1.1", "1.4.1", "…"], "seed": 42, "slice": { "ranges": [[0, 0.5]] } }
```

- **`seed`** orders the (filtered) pool with a deterministic shuffle of **SC order → aspect
  order within each SC → case order within each aspect**. The same seed always yields the same
  order, so multiple annotators sharing a seed share one ordering.
- **`slice.ranges`** keeps only the given fractional ranges of that order (`[start, end)`,
  boundaries at `Math.round(frac × N)`), e.g. `[[0,0.5]]` = first half, `[[0,0.25],[0.75,1]]` =
  first + last quarter.

Ready-made 4-annotator splits of the 10-SC demo set (seed 42, exact 2× coverage, 213 pages
each) live in **`splits/`** — see [`splits/WORK-SPLIT.md`](splits/WORK-SPLIT.md).

## Rebuilding the manifest

`manifest.json` is generated from the 22 `result.json` files plus the hand-authored
`plain-english/<sc>.json` sentences:

```bash
node eval/act-augmented/_annotator/build-manifest.js
```

Trusted Tester methodology text is **not** baked into the manifest (it lives under the
un-tracked `refs/`); the tool fetches it live from `/refs/trusted-tester/` at runtime and
splits it into per-test sections client-side.

The **practice** set is generated separately:

```bash
node eval/act-augmented/_annotator/build-practice.js   # -> practice/practice-cases.json
```

It picks, per SC the annotator covers, one failing + one passing W3C ACT test case
(deterministic, same for everyone; pages must load cleanly offline). The Trusted Tester test
shown for each ACT rule comes from `practice-tt-map.json` for multi-test SCs (single-test SCs
auto-use their sole test; SCs with no TT file show the Understanding doc). Re-run after editing
`practice-tt-map.json`.

### Which TT test shows for each aspect

`manifest.json` carries a per-aspect `ttTests` list. It is resolved at build time:

- **Single-test SCs** (11 of the 17 TT-covered SCs) auto-map every aspect to that one test.
- **Multi-test SCs** (1.1.1, 1.3.1, 2.1.1, 2.4.2, 2.4.6, 4.1.2) use the hand/agent-authored
  `tt-map/<sc>.json` files — each maps an aspect `slug` to the relevant `## Test X.Y`
  id(s) (e.g. `{"data-table-missing-or-suppressed-semantics": {"tests": ["14.A","14.B"]}}`).
  An empty `tests` list means no single TT test isolates that aspect (e.g. SC 1.1.1's
  homoglyph aspect, or SC 4.1.2 name/role aspects TT routes through 5.C/6.A/7.x) — the tool
  then shows the full SC process. Edit these files and re-run `build-manifest.js` to adjust.

## Highlight target resolution & selector overrides

The highlight overlay resolves the target like this (all client-side, no page mutation):

1. Use the page's `highlightSelector` if present, else its `primarySelector`.
2. If that matches **0 elements**, retry with a **base selector** — state pseudos
   stripped (`:focus`, `:hover`, `:visited`, `:checked`, `::before`, `::placeholder`, …).
   If the original was a focus selector, the resting element is then **`.focus()`-ed** so the
   real focus indicator shows (labelled *"target (focused)"*).
3. The target is **scrolled into view** inside the iframe.
4. If it matches but is **hidden at load** (a dialog/tooltip/menu shown on interaction, or a
   `<title>`), a message explains it rather than drawing nothing.

A one-time audit (render every page, test its selector against the live DOM) found 225
selectors that matched nothing / a hidden / a tiny / an off-screen element. Triage:

- **~118 need no data change** — handled by the resolution logic above (state pseudos →
  base element + focus; off-screen → scroll; hidden-on-interaction / `<title>` → message).
- **110 genuine fixes** live in **`selector-overrides/<sc>.json`**, keyed `"<aspect>/<caseId>"`
  → `{ selector, note, appearsOnInteraction }`. These covered: the `primarySelector` field
  holding prose or a CSS `@media{}` rule instead of a selector; wrong combinators
  (`table > tr` never matches — `<tbody>` is implied); stale/invented class names and ids;
  `<svg><title>` / image-map `<area>` targets (no box) re-pointed at the parent control/image;
  and live-region/dialog cases re-pointed at the resting container/trigger with
  `appearsOnInteraction: true`.

After overrides, **0 of 923** selectors match nothing; 858 land on a visible element, 1 on an
interaction element, and 64 are correctly hidden-at-load (31 page `<title>`s + dialogs/menus
shown only on interaction). `build-manifest.js` merges the overrides; re-run it after editing
any `selector-overrides/<sc>.json`. The original `primarySelector` is preserved in the manifest
for provenance; only the highlight uses `highlightSelector`.
