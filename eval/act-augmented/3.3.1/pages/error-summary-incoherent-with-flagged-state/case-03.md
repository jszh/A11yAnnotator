# case-03 — Summary states "There is 1 error" while three fields are visibly flagged

## Scenario
A patient-portal "New patient registration" form (Cedar Lane Family Medicine). A red `role="alert"`
summary at the top declares **"There is 1 error in this form"** and gives one fluent message about Date
of birth. But three fields below are genuinely in error, each with a red border, an inline message, and
`aria-invalid="true"`: **Date of birth** ("31/02/1990" — invalid date), **Mobile number** ("0712" —
too short), and **Postcode** ("ZZ" — invalid). The summary undercounts the real error state by two and
enumerates only the first failure, so a user who trusts the count corrects one field, resubmits, and is
blindsided by the two it never mentioned.

## Attribute tuple + developer persona
- **content-domain:** healthcare / patient registration portal
- **UI-component/pattern:** top-of-form `role="alert"` summary + `<fieldset>`-grouped inline errors
- **host-language construct:** `aria-invalid` + `aria-describedby` on three inputs; singular-count prose in the summary
- **locale/i18n:** en-GB
- **failure-mechanism:** wrong count (undercount) and omitted fields — summary reports 1, page flags 3
- **developer persona:** A developer implemented the inline validation correctly (each field re-checked on submit and individually flagged), but the **summary is generated by a different, older code path** that uses a server-side validator which **short-circuits on the first failure** ("fail fast"): it returns only the first error message and a count of 1, then stops. The inline layer iterates *all* fields; the summary layer stops at the first. The two were never reconciled. Because the QA fixtures happened to have only one bad field at a time, the count discrepancy never appeared until real multi-error submissions.

## Element / selector carrying the issue
`.summary` (the `role="alert"`). It claims "1 error" and lists only Date of birth. The page contains
three `input[aria-invalid="true"]` elements (`#dob`, `#mobile`, `#postcode`), each with a `.msg`. The
incoherence is the stated count/membership (1 / dob) vs. the actual flagged set (3 / dob, mobile,
postcode).

## Exact accessibility mechanism (what AT experiences, why it fails)
A screen-reader user hears the alert: "There is 1 error in this form. Date of birth must be a valid date
in the past." Reasonably trusting that count, they fix the date of birth and resubmit — only for the
form to fail again on Mobile and Postcode, which the summary never surfaced. For a non-visual user the
summary is the primary way to grasp the *scope* of what is wrong; an incorrect count and an incomplete
list mean the user cannot reliably "determine what is wrong." Each enumerated message is individually
fluent and each flagged field is individually well wired (passing 36b590 per indicator), but the
summary as an aggregate misrepresents the number and identity of the items in error.

## Expected ACT-style outcome
**failed**

## Why automated tools miss it
Every flagged field passes 36b590: `aria-invalid="true"` plus a descriptive, associated inline message.
The summary is a valid, visible live region. There is no malformed markup. The failure is a numerical
and set-membership mismatch ("1" claimed vs. 3 flagged; one field listed vs. three flagged). No checker
counts the `aria-invalid`/inline-error fields and compares that tally and membership to the summary's
asserted count — axe/WAVE/Lighthouse have no concept of "the summary's stated number of errors should
equal the number of flagged fields." That cross-tabulation is a human reconciliation.

## Citation
> **WCAG 2.2 Understanding 3.3.1 (Intent), `wcag-understanding/error-identification.html`:**
> "The intent of this success criterion is to ensure that users are aware that an error has occurred and
> can determine what is wrong."

> **G83 (Examples), `wcag-techniques/general/G83.html`:**
> "the form is re-displayed with a text description at the top informing which mandatory fields were
> omitted. Each omitted mandatory field is also identified using a text label so that the user does not
> have to return to the list at the top of the form to find the omitted fields."

(The top description must inform the user *which* fields are in error; reporting "1 error" when three
are flagged fails to convey the true set, so the user cannot determine the full extent of what is wrong.)
