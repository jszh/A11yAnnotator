# case-03 — CAPTCHA refresh: `alt` describes the previous puzzle after "Get a new challenge"

## Scenario
A government DMV registration-renewal wizard (County of Marin), step 3 "Verify you are
human". A CAPTCHA challenge image's `alt` spells out the characters to type
("...Type the characters shown: 7 K 2 Q F."). A "Get a new challenge" button repaints the
image with a brand-new code, but the `alt` (the image's text alternative / accessible
name) keeps describing the FIRST puzzle.

## Attribute tuple
- **content-domain:** government / civic services portal (DMV)
- **UI-component/pattern:** refreshable CAPTCHA challenge image + refresh button
- **host-language construct:** `<img alt>` as text alternative; `src` regenerated by script
- **locale/i18n:** en-US
- **failure-mechanism:** F20 — image src updated periodically/on demand; text alternative not updated (F20 Failure Example 3)

## Developer persona
A state contractor wired a CAPTCHA control into the legacy CMS. The CMS template ships
demo content: the first challenge ("7K2QF") and its matching `alt` were both hand-authored
in the template. The refresh handler, added in a later sprint, regenerates the IMAGE only.
The dev never realised the hand-authored `alt` was a text alternative that also needed
regenerating, so it perpetually describes the demo puzzle.

## Element / selector carrying the issue
`img#captchaImg[alt]` — the `alt` is regenerated never; only `src` is updated by
`#refreshBtn`.

## Exact accessibility mechanism
A screen-reader / braille user relies entirely on the `alt` to know which characters to
type (the glyphs are deliberately unreadable to OCR/AT). At load, `alt` ("7 K 2 Q F")
matches the rendered image: correct, and even a documented good practice (H86). After the
user presses refresh, the canvas shows e.g. "M9XJ4" but `alt` still says "7 K 2 Q F", so
the AT user is instructed to type the wrong code and fails the check every time —
permanently locked out of renewing their registration. The text alternative is no longer
a substitute for the image.

Verified with Puppeteer: after clicking `#refreshBtn`, the image `src` fingerprint changed
while `#captchaImg` `alt` stayed `"...Type the characters shown: 7 K 2 Q F."`
(changed=false).

## Expected ACT-style outcome
**failed** (4.1.2; F20 also lists this under 1.1.1, but the refresh is an interactive named
control, keeping the case in the 4.1.2 dynamic-component limb).

## Why automated tools miss it
The `<img>` ALWAYS has a meaningful, non-empty `alt`, so axe/WAVE/Lighthouse `image-alt`
passes on every sample. A CAPTCHA with descriptive alt is even recommended practice, which
makes the stale-after-refresh failure especially subtle. Detecting it requires triggering
the refresh, then OCR-ing the NEW rendered glyphs and diffing them against the unchanged
`alt` string — no scanner reconciles drawn pixels with the name text.

## Citation
> **WCAG Technique F20, Examples — Failure Example 3:** "The source attribute of images on a
> page is updated periodically using script, but the text alternatives are not updated at the
> same time."
