# case-06 — PASS boundary: multi-select listbox where highlighted options match aria-selected="true" (ATS filter)

## Scenario
A TalentPipe ATS "Filter Candidates" panel uses a multi-select listbox ("Required skills") with five
options: Go, Python, PostgreSQL, Kubernetes, Rust. **Two** options — Go and PostgreSQL — are visually
highlighted (tinted background, bold, with a check mark) and both carry `aria-selected="true"`. The
other three are unselected both visually and programmatically. Crucially, the highlight and check mark
are generated by CSS bound to `[aria-selected="true"]`, so the rendered selection and the exposed
selection cannot disagree. This is the **pass** discriminator for the aspect: the visual state matches
the exposed value.

## Attribute tuple
- **content-domain:** job board / applicant-tracking system (ATS)
- **UI-component/pattern:** multi-select listbox (APG Listbox pattern, `aria-multiselectable="true"`)
- **host-language construct:** `<ul role="listbox">` / `<li role="option" aria-selected>` with `aria-activedescendant`
- **locale/i18n:** en
- **failure-mechanism:** none — control under test; visual selection and `aria-selected` agree for every option

## Developer persona
A developer who followed the APG Listbox pattern correctly: the option's selected appearance is driven
entirely from its `aria-selected` attribute via a CSS attribute selector (`[role="option"][aria-selected="true"]`),
so toggling the attribute updates the highlight and check mark in one place. There is no separate
"visual selected" class that could drift from the exposed state. This is exactly the implementation
that the failing cases (01–05) lack.

## Element / selector carrying the issue
No issue. `#opt-go[aria-selected="true"]` and `#opt-pg[aria-selected="true"]` are the two highlighted
options; `[role="option"][aria-selected="true"]` is the single source of both the visual tint/check
and the exposed state.

## Exact accessibility mechanism (what AT experiences, why it passes)
A screen reader announces "Required skills, listbox, multi-selectable" and, on the two highlighted
options, "Go, selected" and "PostgreSQL, selected"; the other three announce as not selected. What AT
hears matches exactly what a sighted user sees, and the matching candidate list (all of whom have Go +
PostgreSQL) corroborates the selection. The selected state is programmatically present, valid, and
truthfully reflects the component's current state — satisfying SC 4.1.2's requirement that states be
programmatically determinable and kept current.

## Expected ACT-style outcome
**passed**

## Why automated tools miss it
This is the symmetry point that proves the aspect is about value *contradiction*, not attribute
presence. A checker passes this page for a shallow reason — every option has a permitted, valid
`aria-selected` boolean and the listbox carries `aria-multiselectable`, so ACT 4e8ab6 / 5c01ea / 6a7281
pass — and it would pass an otherwise-identical page where `aria-selected="true"` were on the *wrong*
(non-highlighted) options just the same. The checker cannot tell this conformant page apart from a
contradicting one; only a human/vision comparison confirms that the highlighted options and the
`aria-selected="true"` options are the same set, which is what makes this a true pass.
