# case-01 — CRM toolbar: search/gear/envelope icons named from their asset filenames

## Scenario
A SaaS CRM ("Northwind CRM") header has a three-button utility toolbar on the right:
a magnifying-glass link to global search, a gear link to settings, and an envelope
link to the inbox. Each is an icon-only `<a>` wrapping an inline SVG. None has visible
text, but each carries a non-empty `aria-label` — except the labels were never written
for humans: the search icon is `aria-label="img_2031"` (the exported sprite id), the
gear is `aria-label="settings.svg"` (the source filename, complete with extension), and
the envelope is `aria-label="link"` (a placeholder from a scaffold that was never
edited). Every link survives c487ae/F89, yet none tells a screen-reader user what the
link does.

## Attribute tuple
- **content-domain:** SaaS analytics / CRM dashboard
- **UI-component/pattern:** APG `toolbar` of icon-only links (search / settings / inbox)
- **host-language construct:** `<a aria-label="…"><svg aria-hidden="true">…</svg></a>`
- **locale/i18n:** en-US
- **failure-mechanism:** accessible name autogenerated from the asset filename / sprite id / scaffold placeholder — present and distinct, but non-descriptive of purpose

## Developer persona
A front-end engineer wired the toolbar by exporting icons from Figma and pasting each
SVG inline. Their lint rule only enforced "interactive elements must have an
accessible name," so they satisfied it the fastest way available: they copied the
`aria-label` straight from whatever string was already on the asset — the export id
`img_2031`, the filename `settings.svg` — and for the last one typed the placeholder
`link` to make the linter green before standup. The CI a11y check passed, so it shipped.

## Element / selector carrying the issue
- `.tools a[aria-label="img_2031"]` — renders a magnifying glass, links to `/search`
- `.tools a[aria-label="settings.svg"]` — renders a gear, links to `/settings`
- `.tools a[aria-label="link"]` — renders an envelope, links to `/inbox`

## Exact accessibility mechanism
Each `<a>` is in the accessibility tree with role `link` and a non-empty accessible
name taken from `aria-label` (the inner `<svg>` is `aria-hidden="true"`, so the name
is exactly the label string). A screen-reader user pulling up the links list hears
"img_2031, link / settings.svg, link / link, link." None of those identifies the
search, settings, or mail destinations the glyphs depict, so the purpose of each link
cannot be determined from the link text alone, nor from any programmatically determined
context (there is none — these are bare toolbar icons). The name-presence floor
(c487ae / F89) is met, but the descriptive limb of 2.4.4 fails.

## Expected ACT-style outcome
**failed** (SC 2.4.4 Link Purpose (In Context)). c487ae *passes* (each name is
non-empty); F89 does not apply (the image links are named, not unnamed).

## Why automated tools miss it
axe-core, WAVE, and Lighthouse only test that an interactive element has a non-empty
accessible name. `"img_2031"`, `"settings.svg"`, and `"link"` are all non-empty and
mutually distinct, so the "links must have discernible text" rule passes and no
duplicate-name heuristic fires. No tool renders the inline SVG to recognise that the
glyph is a magnifying glass, a gear, or an envelope, and none can judge that a filename
or a placeholder fails to describe the corresponding action. Detecting the mismatch
requires a human to see the rendered icon and compare it to the announced name.
