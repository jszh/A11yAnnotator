# InterA11y compared with GenA11y

What InterA11y takes from GenA11y unchanged, what it changes, and what it adds — with where each design came
from. "GenA11y" means the evaluated adapter in `eval/gena11y/` (`extract_elements.py`, `a11y_detector.py`,
`consts.py`, `helper.py`); "v3" means this repository's harness in `scripts/v3/`.

## 1. Adopted from GenA11y (kept as designed)

| # | GenA11y design | Where in GenA11y | Where in InterA11y |
|---|---|---|---|
| A1 | **One module per success criterion**, with a uniform interface: extract the relevant elements, then detect. | `extract_for_sc` / `detect_for_sc` dispatchers | `src/criteria/<sc>.js`, each exporting the same test-specification interface; `src/criteria/index.js` |
| A2 | **Page-wide coverage**: every element relevant to the criterion on the page is examined, not a sample. | every `extract_*` walks the whole DOM | `identify()` works over the whole `PageModel`, and the screening sweep (M8) reads every element of the criterion's kinds; no sampling anywhere |
| A3 | **One judgment per criterion per page, over a batch of elements** labelled with their XPath, so the model sees siblings and page context together (e.g. same-named frames, a sequence of stops). | `[path: …]` labels, `chunk_data`, one call per chunk | `judge/prompt.js` renders each candidate as `[path: …]`; `judge/judge.js` batches by an evidence-size estimate |
| A4 | **The element's markup** is shown to the model. | `outerHTML` in every prompt | the opening tag (`openTag`) on every candidate card |
| A5 | **Test rules stated per criterion, in GenA11y's prompt format** (*"Analyze compliance with WCAG SC … Test rules: 1. …"*), with GenA11y's rule text verbatim for the six SCs it covers, and its text between the heading and the rules (2.4.4's pass condition) kept as the rubric's `preamble` in every variant. | the `Test rules:` list in each `detect_*` | `rubrics/<sc>.js` rendered by `judge/rubric.js`; also the screening sweep's rules (see M5, M8) |
| A6 | **Violations carry the element's XPath**, so findings join to elements. | output schema `violations[].xpath` | `findings[].xpath`; the same normalisation is used to join with the expert study |
| A7 | **Chunk aggregation**: a failure in any chunk fails the page; a failed chunk is not a pass. | `aggregate_responses` (REPRODUCED > PARTIAL > NOT REPRODUCED; NO VERDICT dropped) | `core/resolve.js`: any FAIL fails the criterion; NO_VERDICT / UNDETERMINED make it INCOMPLETE, never PASS |
| A8 | **Screenshots for visual criteria.** | 1.4.1, 1.4.10, 2.4.10, 3.3.x screenshots | crops and full-page images per candidate (see M6) |

## 2. Modified

| # | GenA11y design | Problem observed | InterA11y design |
|---|---|---|---|
| M1 | System prompt: *"Be precise and avoid false positives — only flag clear violations, not ambiguous cases."* | Biases every verdict toward "no violation" when evidence is incomplete; the adapter misses what it cannot see (e.g. 3.3.1: "if no form or error state is present, the page passes"). | **Neutral evidence standard** (`judge/prompt.js`). Four verdicts — FAIL, PASS, NOT_APPLICABLE, UNDETERMINED. FAIL and PASS carry the same burden: each must name the observation it rests on; *"an absent observation is evidence of nothing"*. UNDETERMINED is reported, not converted into PASS. No instruction to prefer either outcome. |
| M2 | Evidence = the DOM as written (Selenium `outerHTML`, inline style strings). | Markup is not what users get: names computed by the browser differ from attributes; hidden/unrendered elements look like live controls (expert cases C310/C317: GenA11y flagged "focusable" links inside `visibility:hidden` slides). | **`PageModel`** (`model/page-model.js`): the browser's *computed* accessibility tree (role, name, name source, states) joined to each element, plus exposure facts (rendered, box, visually hidden, clipped out, off-page, inert, aria-hidden self/ancestor, tabindex). Markup is still shown (A4), but facts come from the rendered page. |
| M3 | Single-shot LLM call. | The model cannot check anything it is unsure of. | **Agentic judge** (`judge/gemini.js`, `judge/tools.js`): a function-calling loop in which the model can call the criterion's live inspection tools (v3's CDP tools: operate a control, drive a key sequence, force a state and capture it, read the AX node, measure geometry at another width…), each on a fresh copy of the page, within a per-batch tool budget. The tool budget scales with the batch (2 per candidate, 4–24), and each rule names only tools that add evidence the candidate card lacks. |
| M4 | Every element of the criterion goes to the LLM. | Cost, and verdicts on facts a measurement settles exactly. | **Sound deterministic rules decide first, in both directions** (`assess()`): e.g. focus rests on an aria-hidden element → FAIL; a Tab stop's rendering is pixel-identical focused and unfocused → FAIL; a native control in the Tab sequence → PASS for 2.1.1. Only OPEN candidates go to the judge, *with the rule's facts as evidence*; an inconclusive measurement never blocks judgment. |
| M5 | A 2–7 line rule list per criterion. | Some rules are not the criterion (4.1.2 "Links must have valid href values"; "descriptive" names, which are 2.4.6; 1.4.3 "check text readability"); the list omits element kinds the criterion covers (1.4.1 state peers and graphics) and says nothing about when a rule passes, or which tool would settle it. | **The same rules, corrected and annotated** (`rubrics/<sc>.js`): rules or parts that are not the criterion are removed (listed in each file header); missing kinds are added in the same style (`from: 'added'`); each rule names its **tools** and carries a **rubric paragraph** — fails / does not fail, every clause citing its normative source, both sides of each boundary — rendered as two variants: **v1** = rules + tools, **v2** = v1 + rubric. |
| M6 | 3.3.1: one screenshot of the page at rest. 1.4.1: one full-page screenshot. 4.1.2 rule 2 (*aria-hidden must not receive focus*): judged from markup. 1.1.1: markup only (no pixels; vision only for URLs ending in an image extension, for 1.4.5). 1.4.3: inline-style colour strings. 2.4.4: the link's parent/siblings as HTML. | The behaviour or appearance each criterion is about is not in the evidence: no error is ever triggered; states (selected tab, hover) are never produced; focusability is guessed; the image is never seen; colours are read from CSS, not the rendered page; context is structural, not the programmatic context WCAG defines. | **Probes** (`probes/`): forms are submitted empty and with invalid values; peers in different states are compared property by property and link cues read at rest, on hover and on focus; focus is moved by real Tab presses and recorded where it rests; images are cropped from the rendered page; text colour is composited and confirmed against rendered pixels; link context is split into programmatic and merely nearby. |
| M7 | A verdict per page (`REPRODUCED` / `NOT REPRODUCED`). | Cannot tell which element passed, only which were reported. | **A verdict per candidate** with its source (`rule:<id>` or `judge`) and reason, plus the criterion verdict; findings keep GenA11y's `{xpath, reason}` shape. |
| M8 | Per-criterion detector prompt: the criterion's elements with `[path: …]` labels and its test rules, asking the model to *report violations* (under the M1 system prompt). | The model is asked to decide from markup alone, and told to report only clear cases; whatever it does not report is never examined again. Its output is the final answer. | **Screening sweep** (`screen/sweep.js`, `screen/select.js`, `screen` in each `criteria/<sc>.js`). The same input shape — per-criterion element kinds, `[path: …]` lines, chunks, a screenshot, GenA11y's test rules (for the six SCs GenA11y covers; the same style for the other six) — but the question is *which elements should be tested*: those the criterion applies to whose conformance the given information does not settle, likely failures and undecidable ones alike. Selecting is stated not to be a verdict; there is no instruction to avoid reporting (or to over-report). The selected XPaths are **united with the rule-based inventory** as every criterion's candidate set; each candidate then goes through the same sound rules (native candidates) or straight to the same neutral, tool-using judge (sweep-only `screened` candidates, with every probe observation of that element — `screen/screened.js`). Each candidate records its origin, and the report gives the verdict with and without the sweep's candidates. |

## 4. What InterA11y does *not* take from v3

The obligation ledger, dispositions (CLAIM/PARTIAL/PROVISIONAL), sampling of elements, per-rule environment
flags, and the separate LLM lanes. InterA11y has one pipeline: identify → observe → assess → judge → resolve.
The v3 pieces it reuses are measurement functions only, imported through one seam (`src/lib/v3.js`).
