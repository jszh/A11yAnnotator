# SC 4.1.2 Name, Role, Value (Level A) — TT Tests 12.C, 12.D, 2.D (+ covered within 5.C, 6.A, 7.A–7.D)

**TT sections:** 12. Page Titles, Frames, and iFrames; 2. Auto-Updating Content · **Baselines:** 19/21/10/14/6
**WCAG SC 4.1.2:** For all user interface components (including but not limited to: form elements, links, and
components generated by scripts), the name and role can be programmatically determined; states, properties, and
values that can be set by the user can be programmatically set; and **notification of changes** to these items
is available to user agents, including assistive technologies.

4.1.2 is **not a single standalone TT test**; it is woven through several:
- **Form elements:** name/role/value tested within **5.C** (`1.3.1-programmatic-label`) — see
  `sc-1.3.1-info-and-relationships.md`.
- **Links:** name/role tested within **6.A** (`2.4.4-link-purpose`) — see `sc-2.4.4-link-purpose.md`.
- **Images:** name/role tested within **7.A–7.D** — see `sc-1.1.1-non-text-content.md`.
- **Frames / iFrames:** dedicated tests **12.C / 12.D** (below).
- **Notification of automatic changes:** dedicated test **2.D** (below).

> **Removed/obsolete in v5.1.3:** `5.E 4.1.2-change-notify-form` and `6.B 4.1.2-change-notify-links` were
> **removed** (no longer required as of the Section 508 ICT Testing Baseline for Web v3.1, April 2024). Changes
> resulting from user interaction with **forms** are folded into 5.D (3.2.2 on-input, out of our scope); changes
> from **automatic** updates remain in 2.D.

## Test 12.C — `4.1.2-frame-title` (Frames)
**Test Condition:** *Each `<frame>` has a title attribute that describes its content.*
**DNA** if no Frames are identified.

### How to Test
1. Launch ANDI. If a Frame is used, ANDI provides a notification that Frames have been detected. Select "Cancel"
   to test an individual Frame.
2. ANDI lists each Frame and, if available, the associated `title` attribute. If there is no title attribute,
   ANDI reveals an "alert."
3. Select each link to access each frame. Review the Frame to understand its content. Navigate back to the page
   being tested and launch ANDI again.
4. In ANDI, review each frame's corresponding `title` attribute for a meaningful description of content.

### Evaluate Results (PASS if)
1. All frames have a title attribute that describes its content.

### Notes
- `<frame>` is obsolete in HTML5, but testers may still encounter it; it can and should still be accessible.
- Frame content must be tested for conformance with all other applicable tests (12.A/12.B do not apply to frame
  content).

## Test 12.D — `4.1.2-iframe-name` (iFrames)
**Test Condition:** *The combination of accessible name and description for each `<iframe>` describes its content.*
**DNA** if no iframes are identified **or** the iframes are explicitly excluded from the tab order (negative
tabindex).

### Identify Content
Use **ANDI: iframes** to identify all iframes in the tab order.
1. Launch ANDI: iframes to navigate to and highlight iframes on the page. (No iframes module → no iframes.)
2. Use "Next Element" to find iframes that have a **non-negative** tabindex (0, 1) **or no tabindex shown**.
   Test only these `<iframes>`. *(Negative tabindex like -1 = explicitly excluded; do not test.)*

### How to Test
1. Launch ANDI: iframes.
2. Review the ANDI Output for each iframe with a non-negative tabindex (or where tabindex is not defined) to
   determine whether the accessible name and description accurately describe the content of each `<iframe>`.

### Evaluate Results (PASS if)
1. The ANDI Output for each `<iframe>` in the tab order sufficiently describes its content.

### Note
- All iframe content must be tested for conformance with all other applicable tests (12.A/12.B do not apply).

## Test 2.D — `4.1.2-change-notify-auto` (Auto-Updating Content)
**Test Condition:** *The page provides notification of each automatic update/change in content.*
**DNA** if the page content does not update or change automatically.

### Identify Content
Identify content that changes automatically on the page as part of auto-update.

### How to Test
1. Identify how the user is notified of the change in content:
   - a. Identify any **dialogs** that alert the user to changes; determine whether they provide sufficient
     programmatic notification of content changes.
   - b. Identify content changes that result in **focus moving** to the changed content; determine whether
     moving focus is sufficient to notify the user (e.g., by describing the change directly in the content the
     focus moved to).
   - c. Identify content changes occurring in an **ARIA Live Region**:
     - i. Launch ANDI: structures.
     - ii. Click "live regions," then hover over any identified live region (or use ANDI's previous/next element
       buttons to navigate to identified Live Regions).
     - iii. Determine whether the changing content is **contained within** the Live Region.

### Evaluate Results (PASS if ANY true)
1. The page notifies the user about a change via a keyboard-accessible dialog, OR
2. The page moves focus to the changed content, AND the changed content provides sufficient description about the
   change, OR
3. The content that has changed is contained in an ARIA Live Region.

### Note
- This is a test for notification of **automatic** changes. Testing the content before/after the change is done
  in other tests. Changes due to **user interaction** are tested elsewhere (e.g., form elements that change in
  response to user selections → Test 5.D, 3.2.2 on-input).

> **Note on overlap with our 4.1.3 lane:** 2.D's live-region path is essentially the WCAG 2.0-era home for what
> WCAG 2.1 split out as **4.1.3 Status Messages**. TT (WCAG 2.0) has no 4.1.3; the closest manual anchor for our
> status-message instrument is this 2.D live-region procedure (dialog / focus-move / live-region trichotomy).
