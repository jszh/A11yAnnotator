# Completeness derivation — SC 2.4.7 Focus Visible (clearing direction)

**Resolver:** `focus-visible-completeness-v1` · **Clearability:** `closed-scope-clearable` ·
**accessibilitySupportDependent:** `false` (the indicator is perceived visually, without AT mediation).

This document is the analytic basis for the obligation SET that a `NO_BARRIER_OBSERVED` (cleared)
2.4.7 claim must close. Per plan Rule 11, *registration is not correctness*: the obligation set
below is the **worst-case-complete** set, and the build's body-mutation tests drop/weaken any one
of these obligations and assert the clear then rejects.

## What "no barrier" must positively demonstrate

SC 2.4.7 (AA): *when any keyboard-operable UI component has focus, there is a visible focus
indicator.* Clearing it for a target requires closing the following finite state/mode space:

Obligation names are TYPED-OUTCOME flags (same namespace as the catalog `typedOutcomes`), so the
completeness predicate reads measured facts and `registry.validateConsistency` proves each
obligation is a support requirement of the supporting experiment (no namespace drift).

| Obligation (typed-outcome flag) | Why it is necessary (failure mode if dropped) |
|---|---|
| `keyboardReachableInState` | A target a keyboard user cannot reach (upstream trap, broken tabindex) cannot be "operated by keyboard with a visible focus"; clearing it is vacuous. (Rule 14 cross-SC dependency.) |
| `realKeyboardFocus` | The indicator must be the one a real keyboard user sees. Programmatic/`.focus()` styling can differ from `:focus-visible` reached by Tab. Forced focus → false clear. |
| `focusDependentIndicator` | The visible change must appear *because of* focus and be absent without it. An always-on shadow/border is not a focus indicator; treating it as one is a false clear. |
| `obviouslyVisible` | A hairline/sub-threshold change is not a reliable indicator; only an obviously visible one clears. Otherwise → adjudication, not a clear. |
| `hydrationReady` | On an under-hydrated snapshot, JS-applied focus styling (CSS-in-JS, `:focus-visible` polyfills, runtime classes) may not have loaded; concluding presence or absence is unsound. |

## Scope this clear does NOT close

- Other interaction modes for the same component beyond the tested keyboard path.
- Page/process-level conformance — the published claim is observation-scoped to the tested
  element/state/environment and carries `conformanceOutcome: NOT_ASSESSED`.

## Body-mutation expectation

For each obligation `o` above, a test that marks every obligation met *except* `o` must yield a
`PARTIAL`, never a cleared claim. This proves the obligation set is enforced as a whole, not a
satisfiable subset.
