# Completeness derivation — SC 3.3.2 Labels or Instructions, clearing direction

**Resolver:** `all-true-completeness-v1` · **Clearability:** `closed-scope-clearable` ·
**accessibilitySupportDependent:** `true` (a programmatic name is realised through AT) ·
**Experiment:** `field-label-probe`.

SC 3.3.2 (A): labels or instructions are provided when content requires user input. This clear is
**scoped to the LABEL sub-claim only**: a rendered input field with a non-placeholder programmatic
name AND a co-located *visible* label. The harder "sufficient INSTRUCTIONS for a complex format"
sub-case (e.g. a required date pattern) is open-world and is **never cleared here** — at most a
barrier or PARTIAL.

| Obligation (typed-outcome flag) | Why necessary |
|---|---|
| `isUserInputField` | the SC applies to fields that accept input; non-fields are out of scope. |
| `fieldRendered` | a non-rendered field cannot be evaluated for a visible label. |
| `hydrationReady` | labels are often wired late (framework labels, `aria-labelledby` targets); an under-hydrated read is unsound. |
| `programmaticNamePresent` | **universe-closing obligation (part 1).** A non-empty accessible name computed WITHOUT placeholder (placeholder is excluded per AccName); a dangling `aria-labelledby` or empty `aria-label` yields no name ⇒ barrier, not clear. |
| `visibleLabelText` | **universe-closing obligation (part 2).** 3.3.2 needs a *visible* label/instruction; an SR-only label or `title`-only name satisfies 1.3.1/4.1.2 but NOT 3.3.2 ⇒ INCONCLUSIVE, not clear. |

A `<label for>` must target THIS field; a label naming a different field does not clear it. Because
the clear is AT-dependent, the builder additionally requires a declared AT baseline (Rule 12).

## Body-mutation expectation
Dropping any obligation ⇒ PARTIAL. Published claim is observation-scoped, `conformanceOutcome: NOT_ASSESSED`.
