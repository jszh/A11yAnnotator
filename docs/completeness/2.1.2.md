# Completeness derivation — SC 2.1.2 No Keyboard Trap, clearing direction

**Resolver:** `all-true-completeness-v1` · **Clearability:** `closed-scope-clearable` (per-component) ·
**accessibilitySupportDependent:** `false` · **Experiment:** `keyboard-trap-escape`.

SC 2.1.2 (A): if keyboard focus can move TO a component, it can move AWAY using only a keyboard. The
obligation is **local and finite per component**: the normative escape-mechanism set is {Tab,
Shift+Tab, Esc}. We reach the region by real keyboard, then exhaustively try those mechanisms; a
clear is the bounded "at least one mechanism moved focus out without escaping to browser chrome".
The page-wide "no trap anywhere" claim is NOT clearable (open over every region/state); this clear
binds to the single (xpath, 2.1.2, no-keyboard-trap) obligation only.

| Obligation (typed-outcome flag) | Why necessary |
|---|---|
| `keyboardReachableInState` | a component focus cannot reach is out of 2.1.2's "if focus can move to it" antecedent. |
| `focusEnteredRegion` | the escape test is meaningful only once focus is actually inside the region. |
| `escapeProvenForWidget` | **universe-closing obligation.** A real Tab/Shift+Tab/Esc moved focus OUT (or closed the region) within a bounded budget, with no one-way-trap disagreement. |
| `focusStaysInDocument` | "escape" must land on another in-document element — focus lost to the URL bar / a focus-stealing iframe is NOT a valid keyboard escape and is treated as INCONCLUSIVE. |
| `hydrationReady` | trap behaviour is usually JS-driven; an under-hydrated snapshot can falsely look trapped or free. |

A modal that cycles Tab but closes on **Esc** is NOT a trap (Esc is a valid mechanism). A one-way
trap (only one direction escapes) or any focus loss ⇒ INCONCLUSIVE, never a clear. A reproduced
cycle with no escaping mechanism is a sound `BARRIER_OBSERVED`.

## Body-mutation expectation
Dropping any obligation ⇒ PARTIAL. Published claim is observation-scoped, `conformanceOutcome: NOT_ASSESSED`.
