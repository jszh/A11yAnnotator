# Two detector false positives reported on the newly-authored negative cases (2026-08-19)

User-reported, from a run over newly authored hard-negative pages. Five findings were raised; three were
page/fixture issues and are not addressed here. Two were harness defects and are fixed below. A third,
separate observation about the SCORER is recorded in §4 — it is not a bug, and it is not changed here.

Base commit `fedaabb8`. Both fixes were reproduced deterministically on the reported page BEFORE any code
was written, and re-measured on the same page after.

## 1. SC 2.1.2 — a keyboard-operable Close control is an escape

**Reported:** `2.1.2/pages/modal-popover-legitimate-containment-vs-trap/case-07.html`, a GT-`passed` page,
produced five `BARRIER_OBSERVED`. The Close button is keyboard-reachable and Enter closes the dialog; the
probe tried Tab, Shift+Tab, Escape and an advised special key, and never activated it.

**Reproduced** (deterministic, `restrictScs=2.1.2`): 5 × `keyboard-trap-escape` BARRIER_OBSERVED, one per
focusable, with `tabEscapes:false shiftEscapes:false escClosesOrEscapes:false advisedKeyEscapes:false
advised:false cycledBackToStart:true`. The dialog is `<dialog id="refill" open>` — **non-modal**, so Escape
legitimately does nothing, and there is no advisory text. Every one of the runner's four exits fails on a
conformant page.

**Root cause: two lanes answered the same question with different contracts.** The sibling instrument
`kbd-graph.detectKeyboardTraps` ALREADY had this rule and already exempted this exact shape —
`probeCloseEscape`, whose own comment cites it ("a region with a keyboard-operable Close control IS escapable
even if Tab cycles within it (the APG-required modal pattern)"), matching `/close|dismiss|cancel|done|\bok\b|
×|✕|✖|⨉/i` and pressing Enter. The experiment runner simply never called it.

**Fix.** `runKeyboardTrapEscape` now calls the LITERAL kbd-graph probe as a fifth escape route — not a second
copy, because a hand-written duplicate is precisely how the two lanes drifted. It runs last and only when
nothing else escaped, since it is destructive (it dismisses the region). Two supporting changes:
`probeCloseEscape`/`regionEscaped` take the region ATTRIBUTE as a parameter, so the runner can use its own
`data-v3-region` tag without clobbering a tag kbd-graph may have written; and `regionEscaped` now counts a
`<dialog>` that has lost its `open` attribute as dismissed even if author CSS still paints it.

**After:** the reported page yields **0** BARRIER_OBSERVED, with `closeEscapes:true` on all five and every
other measurement unchanged — the containment is still measured, it is simply no longer mistaken for a trap.

## 2. SC 3.3.1 — no automatic detection means no obligation

**Reported:** `3.3.1/pages/error-summary-incoherent-with-flagged-state/case-08.html`, GT-`passed`. The page's
real (telephone) error is correctly identified; the probe manufactured an invalid EMAIL condition in a
`novalidate` form with no email validator and faulted the page for not describing it.

**Reproduced:** 1 × `form-error-probe` BARRIER_OBSERVED on the EMAIL field (`nativeWouldBlock:false
customIdentifies:false unassociatedSurface:null`), while the phone field correctly showed
`customIdentifies:true atRestDeclaredInvalid:true`. The page has `<form novalidate>`, **zero `<script>`
elements**, and an email value that is VALID at rest.

**Root cause.** 3.3.1 is conditional — "IF an input error is AUTOMATICALLY DETECTED…" — and the absence of a
message is AMBIGUOUS between "never detected" (not applicable) and "detected, not described" (barrier). The
probe resolved that ambiguity toward barrier every time. `hasConstraint` treats `type="email"` as proof a
rule exists, but `novalidate` is exactly what switches the UA's detection off. The same function already
draws this distinction elsewhere: framework soft markers are honoured only when an active validator is
DETECTABLE, and bare `type=password` is excluded because server-side validation is invisible to a probe that
never navigates.

**Fix — a five-way conjunction, narrowed twice after it broke existing contract pins.** A barrier is withheld
only when ALL hold: the form declares `novalidate`; the probe FABRICATED the condition (the field was valid
as loaded and is invalid after injection); the page did not mutate the DOM; the page did not intercept the
submission; and no client validator is detectable. Fails OPEN in every direction — an unavailable or
unreadable observer is read as "reacted", so a harness failure can never manufacture an abstain.

Two clauses exist specifically to preserve validated behaviour, and both were added only after measurement:

* **Submit interception.** A form whose own handler calls `preventDefault` IS processing the submission
  client-side and stays on the hook. Detected by patching `preventDefault` on the event from a capture-phase
  listener that runs before any page handler — calling the original immediately (so we still never navigate)
  and flagging any LATER call, which can only be the page's. Reading `defaultPrevented` from a bubble
  listener would be simpler but a page calling `stopPropagation()` would strand it and let the form navigate.
* **Fabricated condition, read from the ACHIEVED state.** `validAtRest && invalidAfterInject`. The first cut
  compared the value the probe MEANT to write, which is wrong: `type=number` runs the value-sanitization
  algorithm on a programmatic set, so `el.value='abc'` silently leaves `''` and the field stays valid — the
  probe moved nothing, and calling that "fabricated" abstained on a pin that must stay a barrier.

**After:** the reported page yields **0** BARRIER_OBSERVED; the email field abstains with
`detectionUnproven:true` and the phone field still shows `customIdentifies:true`.

### 2a. Process note — three narrowings, all forced by existing pins

The first cut (novalidate + no reaction) broke **7** contract pins; the second (adding interception) broke
**5**; the third (adding fabrication, compared against the intended value) broke **1**. None was a stale pin.
`#16 barrier retention` exists specifically to stop this lane eroding, and `C6b`/`C6b2` are the core runner
contract. The shapes they protect are the empty `required` field and the redisplayed still-invalid value —
both cases where the user meets the error by simply pressing submit, so the page's silence is a real failure
however inert the page looks. Only a condition the probe CREATED on a page with no capacity to detect it is
withheld. Recorded because the instinct "the tests are behind the doctrine" was wrong three times running.

## 4. The scorer observation — NOT a bug, and deliberately not changed here

Also reported: the evaluation scorer counted all five `default-shadow` observations as authoritative
barriers, so the quoted FP figure does not represent production-authoritative findings. That is correct, and
it is larger than the two defects above.

**What the probe shows.** On the 2.1.2 page: `claims: 0`, `summary.authoritative: 0`,
`summary.barriersObserved: 0`, alongside 24 shadow observations of which 5 were the BARRIER_OBSERVED at
issue, each carrying `authorityState: "shadow"`. Same picture on the 3.3.1 page (16 shadow, 0 authoritative).

**Why.** `authority.js`'s `AUTHORITY` registry contains exactly TWO entries, both `focus-visual-retry`, both
`shadow`. Every other mechanism has no promotion entry and fails closed to `default-shadow`
(`mayPublish:false`). **No deterministic experiment publishes an authoritative claim at all** — not the trap
probe, not the form-error probe, not `hover-content-tri` — because the promotion gates (`goldSized`,
`sealedEval`, `independentRaters`, `measurementValidated`) have not been passed for any of them.

Meanwhile `scoreCase` collapses four different evidence grades into one bit: an authoritative CLAIM, a
PROVISIONAL ledger fill, a deterministic SHADOW observation, and an LLM rubric `LIKELY_BARRIER` all become
`outcome:'caught'`. `authorityState` / `eligibleForAuthority` / `promotedTo` ride on every observation and are
ignored.

**Retrospective decomposition needs no re-runs** — the fields are already in every `results.json`. The
FN-round-1 slices decompose as:

| lane | pre-rep1 | post4-rep1 | rep2 | rep3 |
|---|---|---|---|---|
| authoritative claim | **0/115** | **0/115** | **0/115** | **0/115** |
| PROVISIONAL fill | 84 | 87 (1 FP) | 86 | 87 |
| deterministic shadow | 19 | 21 | 21 | 21 |
| LLM rubric | 2 | 2 | 1 | 1 |
| **union (the reported headline)** | **105** | **110** | **108** | **109** |

Two things follow. The authoritative row is **zero everywhere** — nothing the harness publishes catches
anything. And the dominant lane is the PROVISIONAL fill (84–87 of ~109), the calibrated-but-non-authoritative
rung, so the headline is predominantly *provisional*, not raw shadow.

**Recommendation (not implemented — it is a framing decision, not a defect).** Stratify rather than rewrite:
record which lane produced each catch and report recall/FP per lane plus the union, with the headline naming
its lane. A few lines in `scoreCase` for future runs, and regenerable retrospectively for every past
artifact. It affects every table in the paper, not just one run, which is why it is recorded here for a
decision rather than changed.

## 5. What the sweep exposed about the metric

Four pages counted as 3.3.1 recall were caught on an element unrelated to their defect, by the very mechanism
just fixed. Page-level scoring cannot tell a real detection from a coincidental one: it asks only whether SOME
in-scope barrier fired somewhere on the page.

That is a sharper problem than §4's lane conflation, and stratifying by authority lane would NOT have exposed
it — it needs ELEMENT-LEVEL attribution: did the flagged xpath correspond to the element the case declares as
carrying the issue? Every act-augmented case states that under **"Element / selector carrying the issue"**, so
the comparison is available, though the field is prose and will not always match mechanically.

Recommended before any further recall reporting: sample caught pages by hand across SCs and measure the
wrong-element rate. If it is low, §4 is presentational. If it resembles 3.3.1's, the headline needs
correcting — and both attributions (lane + element) should land in `scoreCase` in one pass rather than two.
