# Capability-gap analysis — keyboard & focus SCs (2.1.1, 2.1.2, 2.4.3, 2.4.7)

Scope: 27 aspects across four SCs. Each row judges whether the harness's CURRENT capability can
correctly adjudicate the aspect, distinguishing a missing **INSTRUMENT** (can't drive/observe the
interaction) from a missing **JUDGMENT** rubric from a **WIRING** gap. Coverage ∈ {COVERED, PARTIAL, GAP}.

Reasoned from: aspect SLUG + WCAG 2.2 Understanding/Techniques + Trusted Tester v5.1.3 keyboard/focus
procedures + EN 301 549 9.2.1.1/9.2.1.2 + harness code (`exp-runners.js` keyboard-activation /
keyboard-trap-escape, `kbd-graph.js` tab-order + trap detectors, `vision-capture.js` STATE_TRANSITIONS,
`cdp-tools.js`, `order-check.js` visualOrderDivergence, `llm-adjudicator.js` keyboard-operability skill).

## Key code facts grounding the verdicts

- **No arrow-key driving anywhere.** Neither the tab-order instrument, the trap detectors, nor any
  runner ever presses Arrow keys. `collectTabOrder` / `detectKeyboardTraps` / `keyboard-trap-escape`
  drive only `Tab`, `Shift+Tab`, `Escape`, and (trap-escape) one advised key + Close-control activation.
  The adjudicator consumes a `respondsToArrows` fact that is **never collected** (always undefined).
- **`keyboard-activation` (2.1.1) is barrier-only and finite-contract.** It refuses composite/roving
  roles, only attempts Enter/Space, and its pointer-only-secondary-handler check (`secondaryPointerHandler`)
  reads **inline `on*` attributes only** — `addEventListener('click'/'pointerdown')` is invisible.
- **`hasKeyHandler` / `focusRisk` are inline-`on*`-only** (`act-page-collect.js`), so a custom widget
  wired with `addEventListener` reads as having no handler.
- **State transitions are SC-keyed + frozen** (`2.4.7→focus`, `2.4.3→focus`, `1.4.13→hover`,
  `3.3.1/3.3.3→submit`). The 2.4.7 focus pair drives **one element** via `el.focus()` + CDP
  `forcePseudoState(['focus','focus-visible'])` and clips to `element-rect+pad` — **no multi-element tab
  walk**, no forced-colors / AT-cursor render in the focus pair.
- **No reveal-state producer** (`dynamic-subjects.js` exists for provenance but nothing emits
  post-activation subjects); disclosures/modals/menus that expose NEW focus targets are not enumerated.
- **Drag is detected only for 2.5.7** (`probeDraggingMovements`), as a pointer-alternative concern — there
  is **no keyboard-path-parity** check for a draggable as a 2.1.1 function.
- **2.4.3 meaning** = `order-check.js visualOrderDivergence`: column-clustered within-column backward-step
  triage (review-only, uncalibrated) + the `focus-order-meaning-v0` rubric over `[viewport, state-before,
  state-after]`. **No positive-tabindex (F44) flag, no modal-containment direction check.**
- **forced-colors render exists** but only as the LLM-callable `render_with_overrides` tool (viewport or
  one element), **not wired into the 2.4.7 focus pair**; no AT-tracking / high-contrast-mode focus capture.
