# Evaluation Notes — sweetgreen_Menu

## Collector / Driver Issues

- **Appearance shots missing for many elements**: Elements at y>13000 (deep in page) produced no appearance shot (`appearanceShot: ""`). The driver skips shots for off-screen elements or elements too far below the initial viewport.
- **Screenshot crop misses 1px outline**: For in-viewport nav links (els 1–4, 14, 15, 17) the `real-tab-diff` showed `indicatorPresent:True` from `computedOutline:'auto 1px rgb(0,95,204)'` but `visibleDiffPct:0` and all pixel pairs were byte-identical (`max_diff=0`). Root cause: the element bounding-box crop does not include the 1px outline that extends *outside* the box. This is a known driver limitation. These elements DO have the UA browser default focus ring (confirmed via `getComputedStyle` and `matches(':focus-visible')` verification). Verdict corrected to NOT REPRODUCED for 2.4.7 for those elements.
- **el14 (Investor Relations) appearance shot**: `shots/el14.png` is blank/empty (0B or minimal content). The element at y=14566 is far off-screen; the shot area was empty.
- **Footer link appearance shots show menu images**: `shots/el15.png`, `el16.png`, `el17.png`, `el18.png`, `el20.png` all show food photography rather than footer text links. These footer elements (y≈14500–14700) are positioned in a part of the page where the viewport crop captures menu item card images from earlier sections. This is a snapshot fidelity gap — the screenshot area is misaligned with the actual rendered element position. The shots are not useful for color/appearance evaluation of the footer links.
- **el0 (Enable Accessibility) localTabWalk**: `reachedByTab=False, stopsToReach=-1` — the local walk starts at index ~5 before target, but target is at index 0 (first focusable). Edge case: no elements before index 0 to start from. However global tabWalk confirms it IS reachable as the first stop (`inViewport:True, speech:'link, Enable Accessibility'`). Keyboard operability verdict uses global tabWalk evidence.
- **srWalk targetSpeech='paragraph' for CTA links (els 6,7,8)**: The SR cursor lands on the parent `<p>` element rather than the `<a>` inside it. This suggests the SR reading granularity stops at the paragraph level. Not a driver error — this reflects SR behavior where the anchor is read as part of the paragraph flow.
- **srWalk targetSpeech='form' for email input and submit button (els 11,12)**: SR cursor lands on the `<form>` container rather than the individual `<input>` or `<button>`. The form is the SR reading unit at that level. Consistent with expected SR behavior for form regions.
- **el10 (span '18G') srWalk: reachedBySR=false**: The span has `axRole:none, inTree:false` (AX tree prunes it as 'uninteresting'). SR cannot navigate to it directly. Not a driver error — reflects the AX tree's decision to omit this presentational node.
- **"here" link (xpath: /html/body/main[1]/section[7]/ul[1]/li[1]/article[1]/div[2]/p[1]/a[1])**: Found in tabWalk stops but not in the 20 sampled elements. This link text "here" is ambiguous (2.4.4) — it links to a Rosemary Focaccia PDF. Included in summary issues list despite not being a sampled element.
- **Privacy Choices button (xpath mismatch in summary)**: The axe finding cites `#footer-your-privacy-choices-button`; the xpath `/html/body/footer[2]/div[1]/div[4]/ul[1]/li[5]/button[1]` in the issues list is approximate — not a sampled element. The axe `label-content-name-mismatch` rule directly confirms the 2.5.3 failure.
- **31 off-screen focusable elements**: The large number of off-screen tab stops (31/40 = 77.5%) is because the page is very long (~14,700px) and most footer links are naturally off-screen at page load. These are legitimate 2.4.11 findings (focus not visible when it arrives), not driver artifacts. The footer content being off-screen at initial load is expected but the tab walk goes there without auto-scrolling the viewport in all cases.
- **noscript flag**: `scriptsDisabled:false` — page evaluated with scripts enabled. All behavioral checks are valid.
